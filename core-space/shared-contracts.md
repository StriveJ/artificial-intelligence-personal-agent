## Behavior and Installation Boundaries

Event identities/formats are unchanged. `readEventSetAsync` (EVENT_SCAN_SCHEMA=1) shares archive/active-line validation with synchronous reads and yields in batches during global verification. Changes to the active source set, read bytes, archive manifest, or business-day boundary reject the result as event_source_changed. Do not return partial conflict judgments or rescan indefinitely. Final file-digest checks remain synchronous; this is not a cross-process transactional snapshot, and hosts still need the existing task mutex. Large individual reads, JSON parsing, and directory enumeration retain synchronous stages. Capacity conclusions apply only to the reported scale. Batching does not waive damaged archives, incomplete installations, or unknown corrupt caches.

Markdown and persistent metadata are authoritative memory. During index writes, creation provenance, relations, and existing restrictions move into memory-meta entries' index_history (schema 1, body/content digests). Local weights/bodies do not become another fact source. Rebuild uses persisted history. If a cache is corrupt and all current bodies uniquely match exported history, preserve corrupt bytes before rebuilding. Reject overwriting corrupt caches whose history was not exported; not every index is disposable. Export does not promote cached user/model confirmation or lift revocation, sensitivity, or project restrictions. Installation requires memory-index-history-v1; unknown downgrade compatibility is not assumed.

Hub conflict-resolution protocol schema 1 lets a paired user inspect the current full file and original candidates and submit the viewed versions, explicit choice, reason, and confirmation. The instance task lock protects writes; changed files reject overwrite. Original audits remain immutable; decisions use separate synchronizable receipts and preserve original/replaced bytes. Interrupted writes reconcile the same operation without rerunning the model. On further file changes, preserve evidence and allow a freshly viewed explicit decision to supersede the unfinished operation. Concurrent cross-device decisions remain pending review; timestamps/file order do not select a winner. Choosing a full file does not bypass other-source disputes or lifecycle checks.

All abbreviated commands require `--root <instance>`, selected by the operator. Examples do not authorize discovering or operating a real instance.

Default context budgets differ by host: IDE 32000 bytes; Hub 16000 bytes. IDE includes its required execution protocol. Explicit --budget takes priority. An insufficient budget still blocks with completeness reasons; do not remove rules or expand without limit.

Memory retains identity v2. `aipa-memory-meta --id <id> --projects <project> --scope project --valid-from 2026-10-01 --valid-until 2026-11-01 --by-user --reason <explicit-basis>` sets project scope and a business-date interval including the start and excluding the end. Global scope is cross-project but still subject to validity/privacy. `--confirm --supersedes <old-ID>` binds both body versions; --clear-supersedes revokes that decision. Supersession cycles are rejected; unconfirmed/invalid successors cannot suppress old facts. Editing a body invalidates confirmation without relaxing existing project/date restrictions. Revoked/pending-review states survive rebuilding and editing. Identical text distilled in different projects keeps independent identities.

`aipa-search --q <term>|--tag <tag>|--list --json --project <project> --at <business-date>` shares lifecycle filtering and output budgets. JSON can include body_hash, scope, valid_from, valid_until; legacy fields remain. --defer-usage fetches candidates without recording actual use. After a successful answer, consumers register the model-supplied versions through a stable --receipt and `--used '[{"id":"<returned-ID>","body_hash":"<returned-digest>"}]'`, with the original project/at. Replay does not double count; changed receipt content or old bodies on a new receipt are rejected. Decay, growth records, and the receipt commit as one recoverable transaction. Recover through `aipa-distill confirm --recover --json`. String-only IDs and legacy CLI automatic use retain compatibility but not version binding/idempotence guarantees.

`aipa-load --context --host ide|hub --project <project> --root <instance> --budget 32000` returns sections, source digests, capabilities, and omissions. Core policy, IDE execution protocol, and explicit-project project.yaml must exist and be nonempty. Missing/blank/unreadable required files yield blocked / required_context_unavailable / exit 2; issues contain paths/reasons only. Unconfigured/blank personal values.yaml/profile.yaml may be omitted as not-configured; configured values are fully budgeted. Privacy-blocked values/project rules yield required_context_private: do not drop required rules and answer. Profile and lifecycle-filtered preferences/instructions may be privacy-omitted without transmitting blocked bodies. Unreadable/unparseable privacy yields context_privacy_unavailable; insufficient required budget yields required_context_exceeds_budget. Blocked sections are always empty. Hosts must not call every missing-rule failure a budget issue or continue model calls.

Hub validates before retrieval, image, or agenda model transmission and again while building answer context; failures retain original content/reasons. Usage-receipt failure is a separate warning and does not erase a successful answer. Hub execution=disabled; the IDE protocol cannot grant execution through mobile chat. context-completeness-v1 and completeness schema 1 are required: new Hub blocks transmission with old Core lacking the contract, even if an old projection says ready. On-demand memory uses search; structured projection does not claim ordinary file-load accounting.

Shared context includes a required built-in source-attribution protocol, with its own content digest and budget cost. Instructions constrain behavior; their identifiers are not automatically factual evidence. When an output contract supplies an allowed citation-source list, cite only identifiers and exact quotes from that list, and omit unsupported citations when abstaining. This does not remove required rules or change privacy filtering. Built-in protocol provenance is marked `source.kind=builtin`.

Fixed v1 Hub audit event identifiers retain their original serialized attachment projections across program-language changes. Compatibility encodings are explicitly named in source and are separate from English UI descriptions and user-language model output. Never translate a saved event payload under the same identity or weaken the different-content rejection rule; existing personal records remain unchanged.

Shared `user-space/llm-provider.yaml` time_zone (IANA, default Asia/Shanghai) and day_start_hour (0-23, default 6) define the business day. UTC/offset event ts is occurrence time projected into the shared zone. Legacy offset-free ts_local remains readable without retrospectively guessing its original zone. Event identity is valid host/sid/event_id; differing payloads with the same identity all leave the effective set. File order never selects one. An explicit duplicate Hub clock configuration conflicting with Core is rejected. Core and Hub use the shared IANA zone for daily scheduling, report boundaries, agenda interpretation, civil-midnight search quotas, and displayed times. Recurring schedules execute an overlapping daylight-saving wall time once at its earlier occurrence; a nonexistent wall time shifts forward by the transition size. Agenda requests with ambiguous or nonexistent local times require clarification. Day-boundary changes revise affected daily/monthly/yearly reports, with independent retry state per date/period. Changing the shared zone does not rewrite original personal timestamps.

Core consumes agenda schema 1/2 natively. lib/agenda-interface.json declares provider protocol/consumer digests. Hub validates it and installs local bindings/reminder skill without changing Core. `aipa-signal agenda --root <instance> --command list` uses an explicitly registered Hub. Proposals/confirmation retain existing permission, lease, and receipt rules. Removing a provider pauses writes; Core continues reading schema 2. Legacy overlays have backups, digests, and explicit overwrite lists; the updater rejects silent overwrite and requires existing recovery plus synthetic combination acceptance. Origin generates native interface digests with `node lab/support/agenda-interface.mjs --write`; without flags it verifies.

Update declarations include lifecycle/context/clock/event identity/usage receipts/agenda provider capabilities. Metadata-only frameworkPreflight lists read paths and reports dataCompatibility=not-checked / installationAllowed=false. It cannot replace complete data-compatibility checks. Ordinary installation planning can read personal metadata and does not satisfy no-personal-data requirements.

### Restricted Framework Installation

From a verified new artifact, `node scripts/aipa-update.mjs --root <explicit-instance> --artifact <verified-artifact> --framework-only` previews by default; --apply installs. The installed Core's UPDATE_CONTRACT must exactly match a known coordinator generation. Existing Core with missing/unknown declarations is rejected; never execute old instance code to guess capabilities or silently downgrade newer formats with an older coordinator. A first managed installation without Core is separately not-installed.

The target must retain every coordinator-known behavior and identical known format versions, even when a particular personal record is absent. This mode neither opens/traverses user-space nor parses session/budget/queue/usage receipts. dataCompatibility=contract-superset and personalDataInspected=false describe declaration comparison, not record validity. Reject old overlays, missing contracts/behaviors, format differences, local drift, existing staged changes, and content filters. Automated installation does not invoke Git hooks/fsmonitor, external diff/textconv, or commit signing; read-only Git checks do not refresh the index cache. Ordinary planning without this flag still performs data checks.

Preview access lists managed mappings and required installation metadata: instance manifest, upstream baseline, private update preferences/transaction/locks, and Git index/HEAD/tree/config/ignore metadata. This is not zero file access and does not waive a future user's authorization for these reads. Installation does not organize personal records, migrate, answer questions, run reminders, or start real services. Recovery uses the same transaction/saved data_access, needs no repeated framework-only flag, and must not overwrite personal files created during installation. The instance must be quiescent or correctly drained by its host; restart Hub after Core code changes. This mode does not authorize this development session to access real instances.

Hub program updating is separate. Its maintainer copies instance/runtime snapshots and starts candidate code; updateAccess/access in the plan/status disclose those reads. dataAccess=no-personal-data (or framework-only) is rejected as personal_data_access_required before plan acceptance, stopping services, or snapshot creation. Core's restricted-install proof cannot be applied to Hub updating; real deployment needs separate authorization.

Hub binds Core code directory and instance-manifest content digests at process startup. Code changes require restart; query parameters on an entry module do not hot-reload transitive dependencies. Changes/missing files/verification failure block new tasks and model transmission and make readyz return 503. Authenticated status diagnostics can still report core_restart_required. Synchronization retains pulled commits without pushing or automatically rolling back. A new process loads new code; explicitly restoring original bytes can unblock a normally loaded old process. Personal content/configuration is outside the program digest and retains dynamic-read behavior.

If module loading failed or code changed during loading, that process's module cache cannot be reused: restart even after restoring files. Restoring bytes alone can unblock only a process that normally loaded the original code without those failures.

Dependencies and external capabilities follow [Constraints section 1](CONSTRAINTS.md). Core uses Node built-ins/local modules plus Git for installation, updates and synchronization; Hub requires Node >=24 and sharp. External models, push delivery and retrieval require authorization. Platform and version support is limited to the combinations identified by the applicable release record.

## Repository and User Languages

Public repository content is English except localized README files. `display.language` in user-space/overrides.yaml selects model output language, with auto following the current user input. An explicit current-output request takes priority. Mechanical CLI/UI text remains English. Personal input, memory, project content, and stored evidence retain original bytes/languages; changing this preference must not translate or migrate them.
